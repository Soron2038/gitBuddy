# gitBuddy — Review 2026-07-27

**Stand:** `3f928fe` (release: bump to 1.0.3) · **Umfang:** Gesamtprojekt —
Rust-Core, Provider-Layer, SvelteKit-Frontend, Usability & Accessibility.

Alle Zeilennummern beziehen sich auf diesen Commit. Wer den Report später
abarbeitet, sollte bei Abweichungen den zitierten Code-Schnipsel als Anker
nehmen, nicht die Zeilennummer.

## Basis und Methodik

Der Code-Teil ist ein vollständiger Lese-Audit aller 19 Rust-Module und aller
13 Frontend-Dateien. Jeder Befund ist an der Quelle verifiziert; spekulative
Befunde wurden verworfen.

Der **Usability-Teil ist ein statisches Review** — kein Live-Walkthrough. Die UI
lebt in Tauris WKWebView und ist mit Playwright nicht ansteuerbar; ein Start über
`npm run dev` im Browser lässt jeden `invoke()`-Call fehlschlagen, sodass nur
Fehlerzustände sichtbar wären. Grundlage sind daher der Komponenten-Code und die
beiden vorhandenen Screenshots (`01-landing-empty.png`, `02-settings-page.png`).
**Konsequenz:** Ladezustände, tatsächliche Latenz, Fokus-Reihenfolge und
Screenreader-Ausgabe sind aus dem Code *abgeleitet*, nicht *beobachtet*. Die
Kontrastwerte (M18) sind aus den CSS-Variablen gerechnet und belastbar; die
Aussagen zu Fokus-Management (N19, N20) sollten bei einem späteren Live-Test
gegengeprüft werden.

Die drei Audit-Stränge wurden konsolidiert: Wo dasselbe Nutzerproblem in
Backend, Provider und Frontend auftaucht, steht **ein** Befund mit allen
Fundstellen (C1 ist der Hauptfall).

### Top Priority Fix — C1

Solange ein abgelaufener Token, ein Rate Limit oder ein Netzfehler als
„0 waiting · Synced just now" erscheint, ist **jede** Anzeige der App
unzuverlässig. Bei einem Tool, dessen einziger Zweck „sag mir, worauf ich
reagieren muss" ist, ist eine stille Falschanzeige schlimmer als ein Absturz —
der Nutzer merkt nichts und verlässt sich auf leere Listen. C2 und C3 hängen
unmittelbar daran; zusammen bilden sie das Thema „die App verschweigt, dass sie
kaputt ist".

# Critical

## C1 — Provider-Fehler sind für den Nutzer unsichtbar, und der Cache wird trotzdem geleert  ✅ **behoben**

**Severity:** Critical · **Bereich:** Core + Provider + Frontend
**Heuristik:** Visibility of system status (#1), Error recovery (#9)

**Orte:**
- `src-tauri/src/aggregator.rs:459-467` (`merge_result`) und `:148-156` (`tick`)
- `src-tauri/src/provider_util.rs:69-83` (nur 429 → `RateLimited`)
- `src-tauri/src/github.rs:325` (403 → `Ok(None)`)
- `src/lib/data/api.ts:404-411`, `src/routes/+page.svelte:549-554`,
  `src/routes/popover/+page.svelte:405-406` (`last_error` wird nicht gelesen)

**Was passiert:** Drei Schichten arbeiten hier gegeneinander.

```rust
// aggregator.rs:459-467
Err(e) => {
    eprintln!("gitbuddy: {what}[{id}] failed: {e}");
    if matches!(e, ProviderError::RateLimited { .. }) {
        *error_slot = Some(e.to_string());
    }
}
```

`Unauthorized`, `HttpStatus`, `Network` und `InvalidBaseUrl` landen nur auf
stderr — das in einem gebundelten `.app` niemand sieht. Alle drei Provider bauen
sorgfältig einen `ProviderError::Unauthorized(AUTH_HINT)` mit Scope-Hinweis
(`github.rs:24`, `gitlab.rs:21`, `codeberg.rs:19`); der Aggregator wirft ihn weg.

Anschließend überschreibt der Tick den Cache bedingungslos:

```rust
// aggregator.rs:148-156
cache.waiting = snapshot.waiting;   // leer
cache.last_error = snapshot.error;  // None
```

Und selbst wenn `last_error` gesetzt wäre: das Frontend liest das Feld gar nicht.

```ts
// +page.svelte:549-554
const info = await lastSyncInfo();
lastSyncedAt = info.synced_at ? new Date(info.synced_at) : null;   // last_error verworfen
```

**Fehlerszenario:** Der Nutzer rotiert seinen GitHub-PAT (oder die Org aktiviert
SSO-Enforcement). Jeder Fetch liefert `Unauthorized`. Der nächste Tick setzt
`waiting`, `repos`, `releases`, `ci` auf leer, `last_synced_at` auf jetzt und
`last_error` auf `None`. Popover und Hauptfenster zeigen dauerhaft
„Nothing's waiting on you · Synced just now". Der Nutzer hat **keine**
Möglichkeit zu erfahren, dass sein Token tot ist — und verpasst still jeden
Review-Request.

**Fix (drei Teile, alle nötig):**
1. `merge_result`: **jeden** `Err` in `error_slot` schreiben, nicht nur
   `RateLimited`. Besser noch als `Vec<(account_id, String)>`, damit die UI den
   *einen* kaputten Account markieren kann statt global „irgendwas ist kaputt".
2. `tick`: einen Tick, in dem *alle* Provider gescheitert sind, als
   nicht-autoritativ behandeln — den vorherigen Cache-Inhalt behalten statt zu
   blanken. Bei Teilausfall nur die Daten des gescheiterten Accounts stehen
   lassen.
3. Frontend: `info.last_error` im vorhandenen Fehlerbanner (`+page.svelte:1654`)
   bzw. `.err-banner` (`popover:842-844`) rendern. Achtung: das Banner muss
   dafür erst aus dem `{:else}`-Zweig heraus — siehe **M12**.

**Zusammenhang:** M4 (403 wird gar nicht erst als Rate Limit erkannt), M5 (403
wird nicht als Auth-Problem erkannt), M12 (Banner unerreichbar), L9 (kein
Backoff). C1 ohne M12 zu fixen bringt im Startup-Fall nichts.

## C2 — Ein fehlgeschlagener Startup-Restore ist für die gesamte Prozesslaufzeit final  ✅ **behoben**

**Severity:** Critical · **Bereich:** Core
**Heuristik:** Error recovery (#9), User control and freedom (#3)

**Orte:** `src-tauri/src/commands.rs:100-110` (`ensure_initialized`),
`:324-405` (`restore_from_accounts`)

**Was passiert:** `init_attempted` ist ein Write-once-Latch:

```rust
// commands.rs:100-110
let mut attempted = self.init_attempted.lock().await;
if *attempted { return; }
*attempted = true;
```

`restore_from_accounts` ist ausschließlich über `ensure_initialized` erreichbar.
Jeder Account-Restore macht einen echten Netzwerk-Call
(`GitHubProvider::connect` → `fetch_viewer` → `GET /user`, `github.rs:42-46`);
ein Fehler wird `eprintln!`'t und der Account übersprungen (`:373`, `:385`,
`:395`). Es gibt keinen Retry-Pfad.

**Fehlerszenario:** gitBuddy startet per „Start at login". Der Nutzer sitzt im
Zug, das VPN ist noch nicht oben, oder der Corporate-Proxy startet gerade erst.
Jeder `connect` scheitert. `providers` bleibt leer, `attempted` ist `true`.
30 Sekunden später ist das Netz da — aber jeder folgende 5-Minuten-Tick fächert
über eine leere Registry auf, alle `list_*`-Commands liefern leere Vecs,
`last_error` bleibt `None`, und die Fußzeile sagt „Synced just now". Die einzige
Rettung ist ein Neustart der App — den ein Menüleisten-Tool, das man nie beendet,
praktisch nie bekommt.

**Fix:** Nicht auf *attempted* latchen, sondern auf *succeeded*. Konkret: die
IDs der gescheiterten Accounts merken und sie am Anfang jedes `tick` erneut
versuchen. Alternativ den Latch zurücksetzen, wenn
`restored.len() < file.accounts.len()`. Minimum-Variante: den Fehlschlag in
`cache.last_error` schreiben, damit die UI „N Accounts konnten nicht geladen
werden — Erneut versuchen" anbieten kann (setzt C1 voraus).

## C3 — `unwrap_or_default()` + `save` überschreibt bei Parse-Fehler die komplette Settings-Datei  ✅ **behoben**

**Severity:** Critical · **Bereich:** Core · **Datenverlust**
**Heuristik:** Error prevention (#5)

**Orte:** `src-tauri/src/commands.rs:475`, `:630-632`, `:636-638`

**Was passiert:**

```rust
// commands.rs:475
let mut s = settings::load(&app).unwrap_or_default();
match provider {
    Provider::Gitlab | Provider::MpsdGitlab => s.gitlab_base_url = Some(base),
    ...
}
settings::save(&app, &s)?;
```

`settings::load` gibt `Err` zurück bei Lesefehler, Parse-Fehler **und**
nicht unterstützter On-Disk-Version (`settings.rs:197-208`, `:261`). Das in
`Settings::default()` zu verschlucken und dann zurückzuschreiben, zerstört die
Datei.

**Fehlerszenario:** `settings.json` ist unparsbar — von Hand editiert, von einem
Pre-`atomic_write`-Build abgeschnitten (siehe L1), oder von einer neueren
App-Version geschrieben, von der der Nutzer downgraded hat (siehe L2). Der
Nutzer verbindet einen GitLab-Account. `load` → `Err`, `unwrap_or_default()` →
Defaults, `save` ersetzt die Datei atomar. **Scan-Roots, Ignore-Liste,
Editor- und Terminal-Command, alle Notification-Einstellungen und das
Poll-Intervall sind dauerhaft weg** — und der Command gibt `Ok(viewer)` zurück,
also sieht der Nutzer keinerlei Fehler.

**Fix:** Fehler propagieren — `settings::load(&app)?` — damit der Connect laut
scheitert. **Das korrekte Muster steht bereits in derselben Datei:**
`import_config` macht es richtig (`commands.rs:1063`: `let current =
settings::load(&app)?;`). Alternativ den Base-URL-Hinweis überspringen, wenn
`load` scheitert. Nie Defaults über eine Datei schreiben, die nicht geparst
werden konnte.

## C4 — `each_key_duplicate`-Crash bei mehreren Accounts im selben Repo  ✅ **behoben**

**Severity:** Critical · **Bereich:** Frontend · **Render-Abbruch**

**Orte:**
- `src/routes/popover/+page.svelte:921` — `{#each repos as r (r.id)}`
- `src/routes/popover/+page.svelte:978` — `{#each releases as r (r.repo_id + ':' + r.tag)}`
- `src/routes/+page.svelte:1585` — `{#each filteredReleases as rel (rel.repo_id + ':' + rel.tag)}`
- `src/routes/+page.svelte:1508` — `{#each filteredRepos as r (r.id)}`
- Ursache: `src-tauri/src/aggregator.rs:495-501` (`tag_extend` dedupliziert nicht),
  `github.rs:436`, `gitlab.rs:432`, `codeberg.rs:376` (IDs nicht account-/host-qualifiziert)

**Was passiert:** Der Aggregator emittiert bewusst **eine Zeile pro
(Account, Repo)** und dedupliziert nie — `tag_extend` macht schlicht
`out.extend(...)` pro Account. Das Hauptfenster umgeht das für Repos per
Dedup über `html_url` (`+page.svelte:398-417`), das Popover gar nicht, und
Releases werden in **keinem** der beiden Fenster dedupliziert.

Svelte 5.55 wirft bei doppelten Keys **auch im Production-Build**, nicht nur im
Dev-Modus (`svelte/src/internal/client/dom/blocks/each.js:349-355` — der
Non-DEV-Zweig ruft `e.each_key_duplicate('', '', '')`).

Zweite, unabhängige Kollisionsquelle: GitLab-IDs sind `gl:<project_id>`,
Gitea-IDs `cb:<repo_id>` — **nicht host-qualifiziert**. Zwei self-hosted
GitLab-Instanzen haben beide ein Projekt mit ID 7.

**Fehlerszenario A:** Der Nutzer verbindet einen privaten und einen dienstlichen
GitHub-Account, beide Mitglied in `acme/api`. Beim nächsten Tick liefert
`list_repos` `acme/api` zweimal mit identischer `id`. Der **Repos**-Tab des
Popovers wirft `each_key_duplicate`, der Render-Effekt stirbt, der Tab bleibt
bis zum Neustart leer/kaputt. Dasselbe für **Releases** in beiden Fenstern
(beide Accounts sehen `v1.2.0` desselben Repos → identischer Key).

**Fehlerszenario B:** Der Nutzer verbindet `gitlab.gwdg.de` und
`gitlab.mpsd.mpg.de`. Beide haben ein Projekt mit ID 7 → zwei verschiedene
`html_url` überleben den Dedup, aber mit identischem Key `gl:7` → das gesamte
Repo-Grid im Hauptfenster crasht. Schon *unterhalb* dieser Schwelle liefern
`ciByRepo.get(r.id)` (`+page.svelte:1512`) und `selectedCi` (`:501-503`) den
CI-Status der **anderen** Instanz, und ein Klick auf eine Karte markiert beide
als `selected` (`:1513`).

**Fix (beide Teile):**
1. Backend: IDs host-qualifizieren — `gl:<host>:<id>`, `cb:<host>:<id>`. Damit
   verschwindet Szenario B komplett.
2. Frontend: eine gemeinsame Dedup-Helper-Funktion in `$lib/format.ts` (wo
   `humaniseSync` und `hostSuggestions` schon leben), die **beide** Fenster
   nutzen — Repos über `html_url`, Releases über `html_url` bzw.
   `repo_full_name + tag`. Alternativ, wenn doppelte *Zeilen* gewollt sind:
   Key auf `r.account_id + ':' + r.id` umstellen.

## C5 — Notification-Lawine bei Erstinstallation  ✅ **behoben**

**Severity:** Critical · **Bereich:** Core
**Heuristik:** Error prevention (#5)

**Orte:** `src-tauri/src/aggregator.rs:201`, `:285-287`; `src-tauri/src/lib.rs:102-103`

**Was passiert:**

```rust
// aggregator.rs:201 / :285-287
let cold_start = !store.initialised;
...
if cold_start {
    store.initialised = true;
}
```

`spawn_loop` startet `tick()` sofort beim App-Setup. Bei einer **Neuinstallation**
gibt es zu diesem Zeitpunkt noch keine verbundenen Accounts, `fetch_all` liefert
also einen leeren `FetchSnapshot`. `compute_new_events` seedet nichts, setzt
`initialised = true`, und `notifications::save` persistiert das.

Der dokumentierte Cold-Start-Vertrag (`notifications.rs:18-22`: „an upgrade or
fresh install doesn't blast the notification centre with a year of backlog") ist
damit **genau in dem Fall verletzt, für den er geschrieben wurde**.

**Fehlerszenario:** Neuinstallation → App startet, Tick #1 läuft mit null
Providern → `initialised=true`, leere Maps → der Nutzer schließt das Onboarding
ab und verbindet GitHub → `provider_set_token` löst `refresh_now` aus → Tick #2
sieht 40 offene Review-Requests, 6 Releases der letzten 7 Tage und jeden
passenden fehlgeschlagenen CI-Run als **neu** → rund 50 macOS-Notifications
feuern hintereinander weg. Der Nutzer schaltet die Notifications ab, und das
Hauptfeature der App ist tot.

Dieselbe Lawine bei jedem Start ohne Netz/VPN (alle Provider-Restores scheitern,
Tick #1 ist leer, das Netz kommt später) — siehe C2.

**Fix:** Den Seed daran koppeln, dass der Tick tatsächlich verwertbare Daten
geliefert hat. Konkret ein Flag `had_successful_provider: bool` in
`FetchSnapshot`, das in `compute_new_events` hineingereicht wird — `initialised`
nur setzen, wenn mindestens ein Provider abgefragt wurde und `Ok` lieferte.
Sauberer noch: pro Account seeden (`store.seeded_accounts: HashSet<String>`), dann
bekommt jeder neu verbundene Account seinen eigenen stillen Seed-Durchgang.

**Test-Lücke:** `cold_start_seeds_without_emitting` (`aggregator.rs:571`) deckt
nur den Cold Start **mit** Items ab. Der Fall „Cold Start leer, dann befüllter
Tick" ist nicht getestet — genau der Bug.

## M1 — Popover-Onboarding bietet kein OAuth und nur einen Account pro Provider  ⬜ **offen**

**Severity:** Major · **Bereich:** UX
**Heuristik:** Consistency and standards (#4), Flexibility and efficiency (#7)

**Orte:** `src/routes/popover/+page.svelte:600-793`, `:107-109`
vs. `src/routes/+page.svelte:1755-1846`

**Was passiert:** Das Popover ist die Primärfläche der App — als
Menüleisten-Tool ist es das Erste, was ein neuer Nutzer sieht. Sein
Onboarding bietet **ausschließlich PAT-Eingabe**. Der OAuth-Device-Flow,
den README und `docs/DECISIONS.md` als empfohlenen Weg führen („Sign in with
browser (recommended) — No token setup needed"), existiert nur im Hauptfenster
unter Settings.

Zusätzlich:

```js
// popover:107-109
let canAddGithub = $derived(viewer === null);
let canAddGitlab = $derived(gl === null);
let canAddCodeberg = $derived(cb === null);
```

Ein Account **pro Provider**. Das Backend und das Hauptfenster unterstützen seit
M6.3 beliebig viele Accounts pro Provider (Keychain-Layout
`<provider-slug>:<login>`). Und weil `showOnboarding = !connected`
(`popover:106`), verschwindet der Add-Pfad im Popover vollständig, sobald ein
Account verbunden ist.

**Fehlerszenario:** Ein neuer Nutzer installiert gitBuddy, klickt auf das
Tray-Icon und wird aufgefordert, einen Personal Access Token anzulegen — also
GitHub-Settings finden, Scopes verstehen, Token kopieren. Der einfache Weg, den
die App eigentlich hat, wird ihm nie angeboten. Später will er seinen
Dienst-Account dazunehmen: im Popover gibt es keinen Weg dorthin, und dass
„Hauptfenster → Settings → + Add account…" die Antwort ist, steht nirgends.

**Fix:** Den OAuth-Block aus `+page.svelte:1755-1846` in eine gemeinsame
Komponente ziehen (z. B. `src/lib/components/ProviderConnect.svelte`) und in
beiden Fenstern verwenden — das behebt gleichzeitig die Drift-Gefahr. `canAdd*`
auf „immer erlaubt" umstellen und im Popover einen „+ Add account"-Eintrag
anbieten, auch wenn schon Accounts verbunden sind. Zu beachten: OAuth im Popover
braucht M2 als Voraussetzung, sonst verschwindet das Fenster mitten im Flow.

## M2 — Das Popover versteckt sich beim Klick auf seinen eigenen Onboarding-CTA  ⬜ **offen**

**Severity:** Major · **Bereich:** UX
**Heuristik:** User control and freedom (#3), Visibility of system status (#1)

**Orte:** `src-tauri/src/lib.rs:141-148`; `src/routes/popover/+page.svelte:650-656`

**Was passiert:**

```rust
// lib.rs:141-148
#[cfg(not(debug_assertions))]
if let Some(popover) = app.get_webview_window("popover") {
    let popover_clone = popover.clone();
    popover.on_window_event(move |event| {
        if let WindowEvent::Focused(false) = event {
            let _ = popover_clone.hide();
        }
    });
}
```

Bedingungslos. Der zentrale CTA des Popover-Onboardings ist aber genau ein
Browser-Sprung:

```svelte
<!-- popover:650-656 -->
<button class="token-link" onclick={() => openExternal(
  'https://github.com/settings/tokens/new?description=gitBuddy&scopes=repo,read:org')}>
  Create a token on GitHub →
</button>
```

**Fehlerszenario:** Der Nutzer klickt „Create a token on GitHub →". Der Browser
kommt nach vorn, das Popover verschwindet augenblicklich. Der Nutzer legt den
Token an, kopiert ihn — und steht vor einem Bildschirm ohne gitBuddy. Er muss
selbst darauf kommen, wieder aufs Tray-Icon zu klicken. Der eingegebene Zustand
bleibt zwar erhalten (das Fenster wird versteckt, nicht zerstört), aber der
Bruch mitten im ersten Setup ist der schlechteste Moment für so etwas.

Dieser Fehler ist der Grund, warum M1 nicht einfach durch „OAuth ins Popover
kopieren" gelöst werden kann: der OAuth-Flow hat einen laufenden Countdown und
Polling — verschwindet das Fenster dabei, ist der Effekt noch schlimmer.

**Fix:** Auto-Hide unterdrücken, solange das Popover im Setup-Zustand ist. Zwei
Wege: (a) das Frontend meldet per Command/Event einen `sticky`-Modus, den der
`Focused(false)`-Handler abfragt; (b) `openExternal` aus dem Onboarding heraus
öffnet stattdessen das Hauptfenster mit vorausgewähltem Provider und übergibt
den Flow dorthin. (a) ist der bessere Nutzerfluss, (b) der kleinere Eingriff.

## M3 — Disconnect während des Startup-Restores lässt den Account wiederauferstehen  ✅ **behoben**

**Severity:** Major · **Bereich:** Core · **Race Condition**

**Orte:** `src-tauri/src/commands.rs:401-404` gegen `:658-674`
(`provider_disconnect`) und `:687-741` (`accounts_disconnect`)

**Was passiert:** `restore_from_accounts` sammelt in einen lokalen `Vec` und
nimmt den Write-Lock **einmal ganz am Ende** — nach N sequenziellen
Netzwerk-Roundtrips:

```rust
// commands.rs:401-404
if !restored.is_empty() {
    let mut providers = state.providers.write().await;
    providers.extend(restored);
}
```

`accounts_disconnect` und `provider_disconnect` rufen `ensure_initialized`
**nicht** auf, laufen also parallel zu diesem Fenster.

**Fehlerszenario:** Drei Accounts, einer auf einem langsamen self-hosted GitLab
(10 s Connect-Timeout). Beim Start öffnet der Nutzer Settings und trennt den
GitHub-Account. `accounts_disconnect` löscht den Keychain-Eintrag, entfernt den
Datensatz aus `accounts.json` und ruft `providers.write().remove(id)` — ein
No-Op, weil der Restore den Eintrag noch gar nicht eingefügt hat. Danach ist der
Restore fertig und `extend`et den GitHub-Provider (gebaut aus dem inzwischen
gelöschten Token, im RAM noch lebendig) wieder hinein. **Der getrennte Account
pollt weiter GitHub** und taucht weiter in `list_waiting`/`list_repos` auf —
ohne Keychain-Eintrag und ohne Datensatz in `accounts.json`, bis zum Neustart.

Spiegelbild, genauso real: `provider_set_token` verbindet einen Account während
des Fensters mit einem **frischen** PAT neu — `extend` überschreibt ihn mit dem
Provider, der aus dem alten Keychain-Wert gebaut wurde.

**Fix:** `accounts_disconnect`, `provider_disconnect` und `provider_set_token`
zuerst `state.ensure_initialized(&app).await` aufrufen lassen — sie sind die
einzigen mutierenden Commands, die das überspringen. Zusätzlich sollte
`restore_from_accounts` unter dem Write-Lock noch einmal gegen `accounts.json`
prüfen, bevor es einfügt.

**Zusammenhang:** M9 (dieselbe Klasse Problem an `accounts.json`).

## M4 — GitHub-403 bei Rate-Limit-Erschöpfung wird als „kein CI / kein Release" gedeutet  ✅ **behoben**

**Severity:** Major · **Bereich:** Provider

**Orte:** `src-tauri/src/github.rs:325`, fehlendes Gegenstück bei `:369-375`;
`src-tauri/src/provider_util.rs:69-83`

**Was passiert:**

```rust
// github.rs:325
// 403 can happen when the repo's owner has disabled actions for
// forks; treat it the same as "no CI" to keep the batch flowing.
StatusCode::FORBIDDEN => return Ok(None),
```

`provider_util.rs:69-83` klassifiziert **nur 429** als `RateLimited`. GitHub
liefert für Primary-Limit-Erschöpfung und für Secondary/Abuse-Limits aber
**403 mit `x-ratelimit-remaining: 0`**. Kein Provider liest je
`x-ratelimit-remaining`, `x-ratelimit-reset` oder `Retry-After` — null Treffer
im gesamten `src-tauri/src`-Baum.

**Fehlerszenario:** Ein Nutzer mit 3 Accounts × 60 Repos sprengt das

(`if let Ok(Ok(Some(..)))`) verwirft. `merge_result` eskaliert nur `RateLimited`
→ `cache.last_error` bleibt `None`. Der Nutzer sieht einen leeren Releases-Tab
und keine CI-Punkte, ununterscheidbar von „du hast kein CI", ohne jeden Hinweis.

**Fix:** Vor dem 403-Match prüfen, ob `x-ratelimit-remaining == "0"` (oder ein
`retry-after`-Header vorhanden ist) und dann `ProviderError::RateLimited`
zurückgeben. Erst danach auf die „Actions deaktiviert"-Deutung zurückfallen. Am
besten zentral in `provider_util::http_error`, zusammen mit M5 und L9.

## M6 — Unbegrenzter Fan-out: 120 parallele Requests pro Account pro Tick  ✅ **behoben**

**Severity:** Major · **Bereich:** Provider

**Orte:** `src-tauri/src/github.rs:181-189` und `:216-224`; gespiegelt in
`gitlab.rs:199-207`/`:231-239` und `codeberg.rs:148-156`/`:180-188`;
angestoßen von `src-tauri/src/aggregator.rs:381`

**Was passiert:**

```rust
// aggregator.rs:381
let (releases, ci) = tokio::join!(p.list_releases(known), p.list_ci(known));
```

Jede der beiden Seiten startet `MAX_REPOS_TO_CHECK = 60` ungedrosselte
`tokio::spawn`-Tasks. `tokio::join!` führt beide gleichzeitig aus ⇒ **120
gleichzeitige HTTP-Requests pro Account**. `fetch_all:373-384` startet einen

faktisch ein selbstverschuldeter DoS.

`futures::stream::iter(repos).map(...).buffer_unordered(6).collect()`, oder
eine gemeinsame `tokio::sync::Semaphore` über Releases *und* CI legen, damit
beide Pfade sich ein Budget teilen. `futures` ist noch keine Dependency —
alternativ eine Semaphore, die schon über `tokio` verfügbar ist.

## M8 — Jede Settings-Änderung löst einen vollen Netzwerk-Fan-out und Disk-Walk aus  ✅ **behoben**

**Severity:** Major · **Bereich:** Core + Frontend

**Orte:** `src-tauri/src/commands.rs:1006-1017`; `src-tauri/src/aggregator.rs:85-87`;
`src/routes/+page.svelte:2171-2180`

**Was passiert:** `save_settings` ruft `state.settings_reload.notify_one()`. Im
`run_loop` lässt dieses Permit das `tokio::select!` sofort zurückkehren — und
der Ablauf fällt direkt in `tick()`:

```rust
// aggregator.rs:85-87
_ = state.settings_reload.notified() => {
    // Settings changed; the next iteration's tick reloads them.
}
```

Der Kommentar suggeriert, es würde nur der Schlaf neu berechnet. Tatsächlich ist
es ein voller Fan-out über jeden Account (waiting + repos + releases + CI, alles
paginiert) **plus** ein kompletter `local_index::scan` über alle Scan-Roots.

Und der Poll-Intervall-Slider hängt an `oninput`:

```svelte
<!-- +page.svelte:2171-2180 -->
<input type="range" min="1" max="60" step="1"
  value={settings.poll_interval_minutes}
  oninput={(e) => setPollInterval(Number((e.target as HTMLInputElement).value))} />
```

exakt der Rate-Limit-Verbrauch, den die Einstellung verhindern soll. Zusätzlich

1. Backend: Der `settings_reload`-Arm soll die Settings neu lesen und dann

2. Frontend: lokalen `$state` für den Slider-Wert halten und erst bei `onchange`
   (oder debounced) persistieren.

## M9 — `accounts.json` Read-Modify-Write ohne Serialisierung  ✅ **behoben**

**Severity:** Major · **Bereich:** Core · **Race Condition**

**Orte:** `src-tauri/src/commands.rs:121-193` (`migrate_id_scheme_to_v2`),
`:167-172`; `src-tauri/src/accounts.rs:167-172` (`upsert`)

**Was passiert:** `migrate_id_scheme_to_v2` lädt die ganze Datei bei `:122`,
`await`et dann pro Account ein Keychain-Load/Save/Delete (`:148-156` — jeweils ein
`spawn_blocking` ins Security-Framework, das einen Berechtigungsdialog zeigen
kann), und schreibt danach den Snapshot zurück, den es geladen hatte:

```rust
file.accounts = migrated;
...
accounts::save(app, &file)
```

`accounts::upsert` ist ein unabhängiges load→mutate→save ohne Lock. Nichts
koordiniert die beiden.

**Fehlerszenario:** Erster Start nach einem Upgrade von einer v1-`accounts.json`.

neue Datensatz ist weg. Ergebnis: ein verwaistes Keychain-Secret plus ein
laufender In-Memory-Provider, der beim nächsten Neustart aus der Accountliste
verschwindet.

`accounts.json`-Read-Modify-Write legen. Zusätzlich sollten

die Datei anfassen (siehe M3 — dieselbe Ursache).

## M10 — Cross-Provider-Sortierung vergleicht Zeitstempel als Strings in drei Formaten  ✅ **behoben**

**Severity:** Major · **Bereich:** Provider

**Orte:** `src-tauri/src/aggregator.rs:424-425`; `src-tauri/src/types.rs:55`, `:192`

**Was passiert:**

```rust
snapshot.waiting.sort_by(|a, b| b.updated_at.cmp(&a.updated_at));
snapshot.repos.sort_by(|a, b| b.pushed_at.cmp(&a.pushed_at));
```

`updated_at` und `pushed_at` sind rohe Provider-Strings. GitHub liefert
`2026-06-01T12:00:00Z`; GitLab liefert Millisekunden (`…:00.000Z`);
**Gitea/Forgejo rendern RFC3339 in der Zeitzone der Instanz**
(`2026-06-01T14:00:00+02:00`). Lexikographisches `String::cmp` ist nur für ein
einziges normalisiertes Format korrekt.

**Fehlerszenario:** Ein Codeberg-PR, aktualisiert um `14:00:00+02:00` (= 12:00
UTC), sortiert **über** einen GitHub-PR mit `13:00:00Z` (der real eine Stunde
später liegt). Die „neueste zuerst"-Liste im Popover ist um den UTC-Offset der
Instanz falsch. GitLabs Millisekunden-Suffix sortiert zusätzlich unter einen
GitHub-Eintrag derselben Sekunde, weil `'.' (0x2E) < 'Z' (0x5A)`.

**Fix:** Einmal zu `DateTime<Utc>` parsen (`chrono::DateTime::parse_from_rfc3339`
wird in `provider_util.rs:136` und `:169` bereits benutzt) und darauf sortieren.
Alternativ `updated_at`/`pushed_at` schon bei der Konstruktion in jedem Provider
auf UTC-`Z` normalisieren — das ist die robustere Variante, weil es auch M11 und
die Frontend-Anzeige mitheilt.

## N1 — Der 60-Tage-TTL-Prune benachrichtigt erneut über dauerhaft sichtbare Items  ✅ **behoben**

**Bereich:** Core · **Orte:** `aggregator.rs:116-117`, `:211-214`;
`notifications.rs:124-132`, `:24-26`

```rust
let mut store = notifications::load(app);
notifications::prune(&mut store);        // wirft Einträge > 60 Tage weg
...
store.waiting.entry(key).or_insert_with(|| now_ts.to_string());  // nie aufgefrischt
```

Der gespeicherte Zeitstempel ist *first-seen* und wird nie angefasst
(`or_insert_with`). `prune` läuft **vor** dem Diff — ein Eintrag, der über
`TTL_DAYS` altert, wird also entfernt und im selben Tick mit
`already_seen == false` neu eingefügt.

**Fehlerszenario:** Ein Review-Request, der in einer langsamen Org seit 61 Tagen
offen ist. In diesem Tick wird der Key gepruned, das Item als brandneu behandelt,
und der Nutzer bekommt eine „Review requested"-Notification für einen PR, den er
seit zwei Monaten ansieht. Das wiederholt sich alle 60 Tage, solange das Item
offen bleibt — und widerspricht direkt dem eigenen Doc-Kommentar
(`notifications.rs:24-26`).

**Fix:** Den Zeitstempel bei jeder Sichtung auffrischen
(`*store.waiting.entry(key).or_default() = now_ts.to_string()`), sodass die TTL
„seit 60 Tagen nicht gesehen" bedeutet statt „vor 60 Tagen erstmals gesehen".
Alternativ `prune` **nach** dem Diff laufen lassen.

**Test-Lücke:** `prune_drops_only_entries_past_ttl` testet `prune` isoliert. Die
Prune→Diff-Interaktion ist ungetestet.

# Was gut ist — bitte nicht kaputtmachen

Beim Abarbeiten der Befunde oben sollte Folgendes erhalten bleiben:

- **Token-Hygiene ist durchdacht.** `OAuthTokens` hat ein handgeschriebenes
  `Debug`, das `access_token` redigiert (`oauth.rs:89-101`).
  `parse_poll`/`parse_device_code` echoen bewusst keine Response-Bodies.
  `clone_repo` gibt die URL bei Ablehnung nicht aus und pinnt den Clone-Host auf
  den Host des Accounts, **bevor** es libgit2 ein Credential übergibt
  (`commands.rs:930-952`).
- **`keychain::join_failure`** (`keychain.rs:57`) konvertiert einen `JoinError`,
  statt zu unwinden — angesichts des bewusst deaktivierten `panic = "abort"` die
  richtige Entscheidung.
- **`local_index::scan` ist korrekt in `spawn_blocking` gekapselt**
  (`aggregator.rs:436`) — es blockiert die Async-Runtime nicht. (M16 betrifft die
  Kosten, nicht die Kapselung.)
- **`normalise_base_url`** (`provider_util.rs:92-105`) erzwingt `https://` und
  strippt Trailing Slashes, sodass die `format!("{base_url}/api/v4/…")`-
  Verkettungen keine doppelten Slashes erzeugen können.
- **Empty States sind in beiden Fenstern und in jeder `DetailPane`-Sektion
  vorhanden** und gut formuliert. Die Lücken liegen ausschließlich bei den
  *Fehler*-Zuständen (C1, M12, M13).
- **Die Popover-Tabs sind a11y-korrekt** (`aria-selected`, `aria-controls`,
  `role="tabpanel"`, `aria-labelledby` — `popover:811-841`). Sie sind die
  Vorlage, an der sich N16 orientieren sollte.
- **Rune-Hygiene ist sauber:** kein `$derived` mit Seiteneffekten;
  `Set`-typisierter `$state` wird immer neu zugewiesen statt mutiert; die
  Sekunden-`setInterval`-Effekte und der `keydown`-Effekt geben Cleanups zurück.
  `npx svelte-check` läuft mit 0 Fehlern und 0 Warnungen.
- **Loading-States hängen nicht:** beide Fenster löschen `loading` in einem
  `finally`, und `refreshing` hat sowohl einen event-getriebenen Reset als auch
  einen 10-Sekunden-Sicherheits-Timeout.
- **`import_config`** (`commands.rs:1051-1073`) macht das Settings-Handling
  korrekt (`settings::load(&app)?`) — es ist die Vorlage für den C3-Fix.

# Geprüft und sauber — bitte nicht erneut prüfen

Explizite Negativbefunde, damit dieselbe Arbeit nicht zweimal gemacht wird:

- **Alle 23 im Frontend aufgerufenen Commands sind in `lib.rs:56-80` registriert**
  und `#[tauri::command]`-annotiert. Keine Diskrepanzen.
- **Argument-Namen stimmen durchgehend**: das Frontend übergibt
  `baseUrl`/`deviceCode`/`accountId`/`parentDir`/`folderName` gegen snake_case-
  Rust-Parameter — korrekt für Tauri v2s automatische Konvertierung.
- **Kein `unwrap`/`expect` und kein Index-Panic auf produktiven Pfaden.**
  `classify_editor_command`s `.expect("non-empty after trim")` (`commands.rs:1098`)
  ist tatsächlich unerreichbar — `str::trim` und `split_whitespace` verwenden
  dasselbe Whitespace-Prädikat.
- **Kein `std::sync`-Lock über einen `await`.** Alle Locks sind `tokio::sync`, und
  jeder Guard wird vor dem nächsten Await-Punkt fallen gelassen. Der
  `providers.read()`-Guard in `clone_repo` spannt zwar den Match-Block, enthält
  darin aber kein Await.
- **`accounts::make_id`s Lowercasing kollidiert realistisch nicht** — weder
  GitHub noch GitLab noch Gitea erlauben `:` in einem Login, und `url_host`
  strippt Port und Userinfo vor dem Lowercasing.
- **`dedup_by`** (`github.rs:120`, `gitlab.rs:146`, `codeberg.rs:101`) behält das
  erste Element eines Laufs, und der vorangehende Sort stellt die niedrigste
  `reason_priority` nach vorn — der Eintrag mit der höchsten Priorität überlebt
  also korrekt. (Der *Key* ist bei GitLab trotzdem falsch, siehe M7.)
- **`walkdir`s `skip_current_dir` direkt nach dem Yield eines Verzeichnisses ist
  korrekt** (`local_index.rs:100`) — gegen die vendored Quelle
  (`walkdir-2.5.0/src/lib.rs:840-855`, `:1191-1193`) verifiziert.
  `follow_links(false)` schließt Symlink-Schleifen aus.
- **Release-Titel sind sicher**: alle drei Provider fallen backendseitig
  `name → tag_name` zurück, `{r.name}` im Popover kann also nicht leer rendern.
